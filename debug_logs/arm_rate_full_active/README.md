# 2台同時500Hz FB＋DOB制御の結果（2026-09-09）

## 結論

現状のType17個別読出し（位置・速度・電流を各500Hz）に、2台分の電流指令500Hzを加えるとCANキューが溢れた。
DisableでのFB取得500Hzは成立するが、この方式での同時制御は未達。
500Hz化不能と一般化するものではなく、通信の組み立て方を変更する必要がある。

手動Launch manual_joy_ctrl_legacy.launch.py（PID3666369）にSIGINTを送り正常終了を確認。
指令publisherが0になってから試験。Launchは再起動していない。
作業ブランチYasaki_Control_dev、変更未コミット・未Push、復元元stashは保持。

## 試験条件

F7制御タスク2ms、FB要求divider=1。両軸mode4（F7 DOB速度制御→モーター電流モード）。
両軸に速度目標±1度/s・0.5Hzの正弦波、10秒予定。ROS目標送信は約90Hzで、500Hzではない。
ゲインはKp=.17、Ki=.012、filter=.10のまま。DOB電流上限1A、モーター設定上限2A。
RoboMasterは両台とも校正・Enable禁止。F7角度±145度、ホスト変位10度監視を維持。
実機ログ: ../arm_step_20260909_185214/
シリアル: ../arm_500hz_full_active_serial.jsonl
試験ELF SHA256: 2289c5da767327e101bbeb600d83afe2a92e6023e589224922a230bc6d7e0ee0

Type2も各約493回/秒受信。HAL送信エラー・CANエラー・優先キュー満杯は0。
これは物理CANエラーではなく通常ソフトウェア送信キューの過負荷。
制御ループ最大間隔は後半15ms。1秒毎の既存混雑警告UART出力の影響も疑われるが、内訳は未計測。
HAL受付数や送信完了callback数は、各目標のモーター内部実行確認ではない。
rate.csv / rate.binにRAMの1秒集計を保存（停止後SWD HotPlugで取得）。

各軸で、電流指令＋Type2応答の2フレームに、3パラメーターの要求・応答6フレームが加わる。
想定総量は2台×500×8=8000フレーム/秒。従来100Hzの読出しをそのまま500Hzに上げる方式は過大。
FIFO滞留中のmechPosは受信時刻だけ新しくても元の測定は古い可能性がある。今回のログはその遅延を直接測っていない。

## 停止結果

肘の変位10度監視で予定10秒より前に中断。制御性能を正常と判定していない。
肘位置の記録範囲 -106.1958～-95.3462度、根本105.4565～106.9167度。
記録電流ピークは肘1.0753A、根本1.0028A（設定値と電流FBには追従誤差がある）。
Disable serviceは両軸成功。機構端±145度は越えていない。

## 復旧済み

ARM_TEST_FB_DIVIDER=5（各個別読出し100Hz）へ戻してDebug/Releaseビルド・flash verify成功。
F7 DOB演算タスク2ms、ゲイン・電流上限は変更なし。RAM計測機能は残した。

次の候補はType2の位置・速度を利用する、あるいは高精度mechPos/iqfを優先しmechVelのみ低頻度にする方式。
従来要求された個別パラメーター読出しを無断で削除していない。どのFBを500Hz必須とするか区別したうえで設計・再試験する。
